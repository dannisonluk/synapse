## 篩選原則

提案只用三條標準篩：

1. **是否讓「畫布上看到的 = 實際跑出來的」更可信。** 這是本專案的核心不變式
   （見 README §7 與 `engine/csv.ts` 的註解），新功能不該削弱它。
2. **是否讓使用者少猜。** 現在的失敗模式多半是「跑得動但算錯」或
   「不知道資料長什麼樣」，而不是「報錯」。
3. **是否能用現有 harness 守住。** `scripts/verify.mjs` +
   `verify_duckdb_wasm.mjs` + `verify_hermes.py` 已經能跑真引擎、真 Polars。
   若一個功能的驗證只能靠「看起來對」，那它就會變成下一個 §7 的 sharp edge。

難度標記：**S**（一天內）／**M**（數天）／**L**（一週以上，且需要架構改動）。

## Tier 1 — 基礎缺口（低風險、高回報）

這一層的共同特徵：**功能上不新增任何資料能力**，但少了它，其他所有功能都會
被拖慢。建議先做。

### 1.1 Undo / Redo

- **目的**：讓「試錯」變成低成本動作。目前改壞一個節點的唯一回復手段是
  重新拖一個，這會直接抑制使用者探索。
- **適用情境**：調參數、刪錯邊、Hermes 套了一個 patch 之後想反悔、把節點
  拖到別的連線上。
- **實作重點**：
  - 命令堆疊放在 `NymphCanvas` 的 nodes/edges 之上。**不要**每次 state 變更
    就 push —— 表單每打一個字都會觸發 `onChangeConfig`，堆疊會爆掉。
    需要合併（coalescing）：同一個節點的 config 連續變更合併成一筆，
    或在輸入框 blur / 400ms 閒置時才落筆。
  - **已知的衝突點**：`AlteryxNode.tsx` 有一個 `useEffect` 把外部傳入的
    `data.config` 同步回本地 state。undo 會同時改動 nodes 陣列與這個 effect，
    要確認不會互相覆蓋（否則會出現「undo 之後畫面閃回舊值」）。
  - 自動存檔有 800ms debounce、`onCanvasStateChange` 有 250ms debounce。
    undo 之後必須強制刷新一次 autosave，不然還原的狀態可能沒被寫入。
- **難度**：M
- **可被 verify 守住**：可以。命令堆疊是純邏輯，可抽成 `engine/history.ts`
  （零依賴），斷言「合併規則」「redo 在 push 後清空」「深度上限」。

### 1.2 執行快取（內容雜湊 + DAG 級 memo）

- **目的**：現在點一個節點會**重跑整個上游子圖**。調下游參數時，上游那些
  昂貴的掃描與聚合全部重做一次。這是目前最大的時間浪費。
- **適用情境**：反覆調一個 SUMMARIZE 的聚合函數；改了末端 FILTER 但上游
  有 JOIN + 大表掃描；反覆試同一個節點的不同設定。
- **實作重點**：
  - 快取鍵 = `hash(nodeType + normalizeConfig(config) + 上游快取鍵 + 資料版本號)`。
    遞迴定義，所以上游任一環變更就自動失效。
  - **`normalizeConfig` 是必要的**，不能直接雜湊原始 config：鍵的順序、
    未清理的預設值、Hermes 塞進來的多餘鍵都會讓雜湊不穩定，於是快取永遠
    不命中（而且不會報錯，只會「好像沒生效」）。
  - **資料版本號是關鍵**。`useUpstreamColumns` 的 `refreshKey` 用的是
    `sqlQuery` 字串；但重新上傳同一個 CSV 時 SQL 沒變、資料變了。
    所以要有一個每次 `registerLocalFile` 就 +1 的計數器進到鍵裡。
    少了這個，使用者會看到舊資料而完全沒有提示 —— 正是最糟的失敗形態。
  - 命中時不能只跳過編譯，要真的跳過 `CREATE OR REPLACE TEMP TABLE`。
    用 `ikaros.tables()` 確認輸出表還在（使用者可能清了引擎）。
  - 匯出（SQL / Polars）**不受快取影響** —— 匯出永遠重新編譯。
- **難度**：M
- **可被 verify 守住**：可以，而且是本清單中最好守的一項。純函式
  `cacheKey(node, upstreamKeys, dataVersion)` 直接斷言；再用真引擎斷言
  「改了上游 → 下游鍵改變」與「只改註解 → 鍵不變」。
- **風險**：快取是「靜默錯誤」的溫床。任何不確定都應該**重跑**，
  不要命中。

### 1.3 `ASSERT` 節點（資料品質閘門）

- **目的**：把「資料不對」從「看得出來」變成「跑不動」。目前的管線錯了
  只會安靜地產生錯誤的表。
- **適用情境**：宣告主鍵唯一、宣告某欄不得為 NULL、宣告列數落在預期區間、
  宣告一個自訂述句必須成立。適合放在 `OUTPUT` 之前當守門。
- **實作重點**：
  - **架構上幾乎不用改**：`scheduler.findDescendants` 已經有失敗傳播機制，
    ASSERT 只要「拋錯」就能自動擋掉所有下游 —— 這正是它該做的事。
  - 節點要產生**兩張東西**：passthrough 的輸出表（下游照常連），
    以及一條會在條件不成立時失敗的陳述。`compileNodeStatements` 已經支援
    多陳述（FILTER 就是這樣做的），所以不需要新機制。
  - **DuckDB 端要實測**：需要一個能主動拋錯的函式（`error('...')`）。
    **先探這個 build 有沒有它再寫斷言** —— 這是本專案的既有紀律，
    而空間擴充那輪已經證明「文件有寫」不等於「這個 build 有」。
    若沒有，退路是 `CHECK` 約束或除零，但兩者都比較醜。
  - **Polars 端反而更乾淨**：直接 `raise ValueError(...)`，是一條真的
    Python 陳述。這個不對稱要寫進匯出腳本的 notes。
  - 失敗訊息必須**指名哪一條斷言、哪個欄位、實際值是多少**，
    否則使用者只知道「失敗了」。
- **難度**：S～M（若 `error()` 存在就是 S）
- **可被 verify 守住**：可以，而且是**最該**守住的一項 —— 它是使用者信任
  整個系統的支點。斷言「條件成立時跑得過」「不成立時拋錯且訊息含欄位名」
  「下游真的被擋住」。

### 1.4 節點資料剖面（profiling）

- **目的**：回答「這張表長什麼樣」。現在唯一的資訊是前 5 列預覽，
  使用者無法看出 NULL 比例、基數、值域 —— 而這些正是決定下一步的依據。
- **適用情境**：決定 JOIN 鍵之前；發現某個聚合結果異常；接手別人
  的工作流；確認 IMPUTE 有沒有補對。
- **實作重點**：
  - 每個欄位：列數、NULL 數、distinct 數、min/max、型別。
    這是對每欄一次 `COUNT` / `COUNT(DISTINCT)` / `MIN` / `MAX`，
    可以在**一條** SQL 裡做完，不要每欄一個 query。
  - **成本必須是使用者主動觸發的**。不能在每次執行都算 —— 那等於每次
    執行都多一次全表掃描。做成面板上的一顆按鈕。
  - **剖面結果絕對不能寫進 `config`**。`types/nodeConfig.ts` 是「驅動 SQL
    的形狀」，剖面是衍生事實；寫進去會污染 workflow 存檔、讓快取鍵不穩定，
    而且會隨存檔一起傳出去。放元件 state。
  - `COUNT(DISTINCT)` 在超高基數欄位上很貴 → 超過門檻要改用估算或標註。
- **難度**：S～M
- **可被 verify 守住**：可以。斷言產生的 SQL 在真引擎上對已知 fixture
  給出正確的 NULL 數 / distinct 數（含 NULL 與空字串要分開算）。

### 1.5 OPFS 持久化（解決「重載要重新上傳」）

- **目的**：解決 README §7 已列的限制 —— 存檔只記了表名，沒記檔案位元組，
  所以重載後必須重新上傳 CSV。
- **適用情境**：跨工作階段的長流程；同一個 CSV 反覆使用；
  「我昨天做到一半」。
- **實作重點**：
  - duckdb-wasm 可以掛 OPFS 後端的虛擬檔案系統。`safeVirtualFileName`
    已經存在，命名紀律不用重做。
  - **一定要 opt-in，而且要有「清除本機資料」按鈕**。這改變了隱私性質：
    資料從「只在記憶體」變成「落在磁碟」。使用者必須知道，而且能一鍵抹掉。
  - 需要 **schema 版本號與遷移策略**：OPFS 裡的表會比程式碼活得久。
    程式碼升級後讀到舊格式要有明確行為（重建而不是壞掉）。
  - 配額問題要處理（同 `persistence.ts` 對 localStorage 的做法：安靜失敗
    並告知，而不是拋錯）。
- **難度**：M
- **可被 verify 守住**：部分。OPFS 需要瀏覽器環境，Node 裡測不到。
  可守的是「虛擬檔名生成」「版本號比較」「配額失敗的降級路徑」——
  把決策邏輯抽成純函式，把 OPFS 呼叫留在薄邊界。

### 1.6 命令面板（⌘K）

- **目的**：27 個節點用拖的已經開始吃力，而且「執行 / 匯出 / 跳到某節點」
  目前都只能靠滑鼠。
- **適用情境**：鍵盤使用者；記得節點名字但找不到它在哪個分類；
  在 20 個節點裡跳到某一個。
- **實作重點**：
  - **搜尋語料已經現成**：`nodeCatalog.ts` 的 `whenToUse` 欄位本來就是寫給
    LLM 看的自然語言描述（「使用者說『輸出 / 下載 / 匯出成檔案』時」），
    拿來做模糊搜尋剛剛好。這是本清單中「投入產出比最高」的一項。
  - 需要處理按鍵衝突：React Flow 自己會攔鍵盤事件，要確認 `⌘K`
    在畫布有焦點時仍然攔得到。
  - 不要引入模糊搜尋套件 —— 27 個節點用簡單的
    「前綴 > 子字串 > whenToUse 命中」排序就夠，而且可以零依賴、
    可以進 verify。
- **難度**：S
- **可被 verify 守住**：可以。排序函式是純函式，斷言
  「打 'join' 第一個是 JOIN」「打 '下載' 命中 OUTPUT」
  「每個目錄條目都能被至少一個關鍵字找到」（防止新節點沒有可搜尋的文字）。

## Tier 2 — 產品差異化

這一層會決定 Synapse 跟「手寫 SQL」的差別在哪。

### 2.1 Alteryx `.yxmd` 匯入

- **目的**：這是整個產品的遷移路徑。能匯入既有 Alteryx 工作流，
  就有真實的採用理由。
- **適用情境**：公司已有一批 `.yxmd`；想評估搬到瀏覽器要多少工；
  想用 Synapse 的匯出來驗證自己對舊流程的理解。
- **實作重點**：
  - `.yxmd` 是 XML：`<Node ToolID>` + `<GuiSettings Plugin="...">` 決定工具種類，
    `<Connections>` 決定邊。節點 id 對映到我們 27 種。
  - **誠實的範圍是「我們支援的那 15 種工具，其餘一律降級成 passthrough +
    明確警告」**，而不是假裝能全吃。要產出一份匯入報告：
    哪些工具成功、哪些被跳過、哪些欄位對不上。
  - 最大的障礙不是工具對映，是**運算式語言**。Alteryx 有自己的公式語法，
    我們現有的 `FORMULA` 翻譯器（`filterExprToPolars` 那條路）是刻意窄的。
    匯入時要能拒絕，並把原文留在節點裡讓人自己改。
  - 邊的 handle 對應要小心：Alteryx 的 Filter 是 True/False 兩條輸出，
    跟我們一樣；但 Join 的 L/R 順序在 XML 裡的表達方式要實測確認。
- **難度**：L
- **可被 verify 守住**：可以，而且是**必須**。匯入的 XML 與我們內部
  DAG 的對映是純函式，fixture 用真實 `.yxmd` 檔（去識別化）。
  斷言「工具對映」「連線順序」「不支援的工具產生警告而不是靜默丟掉」。
- **風險**：若只做半套，使用者會拿到一個「看起來匯入成功但算錯」的圖 ——
  這是本專案最忌諱的失敗形態。所以匯入報告不是加分項，是必要條件。

### 2.2 dbt 匯出

- **目的**：把原型變成正式資產。Synapse 的 DAG 本質上就是 dbt 的 DAG，
  現在只差把 CTE 腳本拆成模型檔。
- **適用情境**：在 Synapse 裡設計好流程，想交給資料工程團隊進 production；
  想用 dbt 的測試與文件能力。
- **實作重點**：
  - 現有的 `exportToSqlCte` 已經產生正確的 CTE 依賴圖，**邊際工作量在
    命名與檔案佈局**：節點 id → 合法 model 名（`node_a` → `stg_a`）、
    `INPUT_DUCKDB` → `sources`、`OUTPUT` → 最終 model 或 exposure、
    `requiredExtensions()` → `pre_hook: LOAD spatial`。
  - **`ASSERT` 節點（1.3）可以自動變成 dbt 的 `tests`** —— 兩者語意相同。
    這兩項一起做，dbt 匯出的價值會跳一級。
  - 視窗函數、聚合、PIVOT 產生的 SQL 本來就是合法 SQL，不用改。
  - 要產出完整的 `dbt_project.yml` + `profiles.yml` 範例，不然使用者拿到
    一堆 `.sql` 也不知道怎麼跑。
- **難度**：M
- **可被 verify 守住**：可以。斷言產生的檔案集合、`{{ ref() }}` 依賴是否
  與 DAG 拓撲一致、model 名是否合法（無大寫、無保留字）。

### 2.3 Macro / 子工作流

- **目的**：把一組節點收成一個可重用的方塊。目前重複的邏輯只能用複製貼上，
  改一處要改十處。
- **適用情境**：公司統一的地址清理流程；同一個 join + filter + aggregate
  在五個地方用到。
- **實作重點**：
  - 這是**架構改動**，不是加一個節點：目錄的 `inputs` 目前是
    `0 | 1 | 2 | -1` 這個封閉集合，而 macro 有「自己宣告的埠」。
    目錄結構要能表達「可變埠」，`resolveSourceTables` 的推導也要跟著改。
  - 編譯方式是**內聯展開**成 CTE，不是產生函式。所以 macro 內部節點 id
    要加前綴去重，而且**必須有遞迴/循環防護**（macro 內用 macro）。
  - 序列化格式要版本化 —— macro 定義會存在 workflow JSON 裡，
    舊檔讀進來要有明確行為。
- **難度**：L
- **可被 verify 守住**：可以。斷言「展開後的 CTE 與手動展開等價」
  「重複使用同一個 macro 兩次不會 id 衝突」「自我遞迴被拒絕」。

### 2.4 遠端 Parquet over HTTP（range request）

- **目的**：不用下載就能分析大檔。duckdb-wasm 支援對 HTTP 上的 Parquet
  做 range request，只抓需要的 row group。
- **適用情境**：S3 / 物件儲存上的公開資料集；10GB 的 Parquet 只想看幾個欄位。
- **實作重點**：
  - 成敗**完全取決於伺服器的 CORS 與 range 支援**。失敗訊息必須說清楚
    是「伺服器不支援 range」還是「被 CORS 擋掉」，不能只說 fetch failed。
  - **兩個引擎會不對稱**：DuckDB 能惰性讀 HTTP，Polars 匯出的腳本不行
    （會變成整檔下載）。這個差異要寫進 notes，不能讓匯出的腳本看起來
    跟畫布一樣。
  - 隱私：URL 會離開瀏覽器。要讓使用者知道自己正在抓外部資源。
  - 現有的 `registerFileBuffer` 是「整個檔案進記憶體」，這條路要另外走
    `read_parquet('https://...')`，不能複用。
- **難度**：M
- **可被 verify 守住**：部分。需要真的 HTTP 伺服器 → harness 可以起一個
  本機 server 提供 Parquet（用 Node 的 http），斷言 range 請求的行為。
  但 CORS 相關的行為測不到，只能靠訊息品質。

### 2.5 執行計畫（EXPLAIN）檢視

- **目的**：讓「為什麼這麼慢」變成可回答的問題。
- **適用情境**：JOIN 很慢；某個節點掃了整張表；想確認 filter 有沒有下推。
- **實作重點**：
  - `EXPLAIN` 的輸出格式在不同 DuckDB 版本間會變，**只做顯示不做解析**。
    任何依賴 plan 文字結構的功能都是未來的維護債。
  - 放在節點的 SQL 預覽旁邊（那裡已經有 `showSqlPreview` 的 UI 模式）。
- **難度**：S
- **可被 verify 守住**：可以（弱）。斷言 `EXPLAIN <compileNodeSelect 的輸出>`
  在真引擎上不拋錯即可 —— 這仍然有價值，因為它順帶證明每個節點的
  查詢都是合法的。

## Tier 3 — Agent 深化

現在的 Hermes 是「一句話 → 一張圖」。這一層讓它在既有圖上工作。

### 3.1 DAG → 自然語言說明

- **目的**：文件化與交接。目前一個 20 節點的圖只有作者看得懂。
- **適用情境**：交接給同事；回顧兩週前的自己；code review 一個工作流。
- **實作重點**：
  - **骨架要由編譯器產生，不能由模型自由生成**。每個節點的
    `compileNodeSelect` 輸出就是事實；LLM 只負責把它寫成人話。
    直接讓模型「描述這張圖」會產生幻覺步驟 —— 而這正是本專案
    一貫拒絕的模式（見 `exportPolars` 對無法翻譯的節點留 TODO 而非猜）。
  - 便宜的落地點：把節點註解寫進匯出的 SQL / Polars 腳本
    （`-- 步驟 3：篩選 amount > 1000`），零 LLM 成本就有七成價值。
  - 需要快取（以 DAG 雜湊為鍵），否則每次開啟都重新生成。
- **難度**：S（註解版）～ M（LLM 版）
- **可被 verify 守住**：可以。斷言「每個節點都出現在說明裡」
  「說明中的欄位名全部存在於該節點的 schema」—— 後者是防幻覺的關鍵。

### 3.2 Patch 預覽 / 核准-拒絕

- **目的**：現在的自我修正迴圈是自動套用的。使用者看不到改了什麼，
  也沒機會拒絕 —— 這對「會動到我資料的東西」是錯的預設值。
- **適用情境**：Hermes 想改一個你已經調好的節點；不確定它為什麼要動。
- **實作重點**：
  - 管線已經齊了：`resolveAstPatch` + `auditAstPatch` 已經會回報四類問題。
    缺的只是 UI：並排顯示變更前後的節點/邊、把 audit 結果顯示出來、
    套用或丟棄。
  - 要能區分「新增」與「修改」—— 修改既有節點比新增危險得多，
    應該預設要確認。
- **難度**：M
- **可被 verify 守住**：可以。`auditAstPatch` 的覆蓋率本來就有斷言；
  補上「預覽產生的 diff 與實際套用的結果一致」。

### 3.3 局部節點編輯（選一個節點描述修改）

- **目的**：不用為了改一個條件而重新描述整個流程。
- **適用情境**：「把這個 filter 改成大於 5000」「這個 join 改 left join」。
- **實作重點**：
  - 上下文只給**這一個節點 + 上游 schema + 下游期望**，不給整張圖。
    便宜很多，也準確很多。
  - 回來的 config 一定要過 `normalizeConfig`，幻覺鍵會被丟掉 ——
    這個機制已經存在，直接複用。
  - 只需要 schema、不需要資料（隱私 + 成本）。
- **難度**：M
- **可被 verify 守住**：可以（`normalizeConfig` 已有斷言，補上
  「未知鍵被丟棄且不影響既有鍵」）。

### 3.4 語意化 join key 建議

- **目的**：JOIN 鍵猜錯是最常見的錯誤之一，而且錯了通常不會報錯。
- **適用情境**：兩張表都有 `cust_id` / `customer_id` / `CustID`。
- **實作重點**：
  - **先做確定性的部分**：正規化後名稱相等（大小寫、底線、`_id` 後綴）、
    型別相容、基數接近。這一段零成本、可測、而且能解掉大部分情況。
  - LLM 只當平手時的裁判，而且只送 schema。
  - 這跟 `FUZZY_JOIN` 那輪的教訓相同：**確定性的部分才是可驗證的部分**。
- **難度**：S（確定性）～ M（加 LLM）
- **可被 verify 守住**：可以。純函式，fixture 用各種命名變體。

## Tier 4 — 信任與交付

### 4.1 工作流快照測試（CI）

- **目的**：使用者自己的工作流也能有回歸保護。現在 harness 守的是引擎，
  不是**你的**管線。
- **適用情境**：一個跑了半年的流程，改一個節點後想確認結果沒變。
- **實作重點**：
  - 格式：`{workflow.json, input.csv, expected.csv}` 三件一組。
  - **這正是 harness 已經在做的事**（section 11 的 fallback pipelines
    就是 prompt → patch → SQL → 真引擎 → 斷言 rows）。缺的只是
    「吃使用者提供的 fixture」這條路徑。
  - 輸入資料要能重現 —— `raw_data` 的 seeding 要固定，不能依賴隨機。
  - 浮點與排序：斷言要能容忍欄位順序與浮點誤差，否則會出現假紅燈。
- **難度**：M
- **可被 verify 守住**：它本身就是 verify 的擴充。

### 4.2 跨引擎等價檢查

- **目的**：證明「匯出的 Polars 腳本算出來的跟畫布上一樣」。
  這是整個雙引擎設計最大的未驗證假設。
- **適用情境**：交付 Python 腳本給別人之前。
- **實作重點**：
  - 技術路徑是 Pyodide + polars。**可行性必須先實測** ——
    polars 是否提供 Pyodide 可用的 wheel 是關鍵未知數，
    而且載入成本可能超過 10 秒。
  - **若做不到，誠實的替代方案是「交給 Colab 執行」**：產生一個
    可貼上的 notebook，附上期望結果。不要為了宣稱有這功能而做一個
    半殘版本。
  - 這條與本專案「先探再寫」的紀律一致：先寫一支 probe 確認 Pyodide
    能不能 `import polars`，再決定要不要立項。
- **難度**：M～L（取決於 probe 結果）
- **可被 verify 守住**：可以（若能跑起來）。

### 4.3 `IN_DB` 的重新定義

- **目的**：這是 Alteryx 覆蓋率的最後一塊。但它**在瀏覽器裡沒有原意**。
- **適用情境**：想寫回外部資料庫。
- **實作重點**：
  - **先講清楚做不到的部分**：第 13 輪已實測 —— wasm 沒有網路，
    `INSTALL spatial` 是 no-op（因為抓不到）。任何需要下載擴充的功能
    （`postgres_scanner`、`httpfs`）在 wasm 裡都不成立。
    所以「連到外部 Postgres」不是難，是**不可能**。
  - 誠實的替代：(a) 寫回記憶體內的具名表（`OUTPUT` 已經在做）、
    (b) 匯出 `.duckdb` 檔或 Parquet 包讓人自己載入、
    (c) 產生一段 `COPY ... TO 'postgres://...'` 的 SQL 讓人拿去跑。
  - (c) 最誠實：Synapse 負責產生正確的語句，執行留給有連線的環境。
- **難度**：S
- **可被 verify 守住**：可以（只驗語句生成，不驗執行）。

### 4.4 SQL 匯入（誠實版）

- **目的**：把既有的 SQL 帶進來。
- **適用情境**：手上已經有一支 200 行的 CTE 查詢。
- **實作重點**：
  - **任意 SQL → 固定節點詞彙是損失性的**，不可能完美。誠實的做法是：
    用 `sqlglot`（後端已有 Python）解析，能對映的（FROM/JOIN/WHERE/
    GROUP BY/ORDER BY）就對映，其餘**明確拒絕並回報**。
  - 注意 `SQL_CUSTOM` 節點已經被移除了（README §7 有記錄），
    所以不能再走「整段 SQL 塞進一個節點」這條路 —— 除非重新引入它，
    但那就等於放棄可視化，要先想清楚。
  - 拒絕優先（refuse-first）與現有 `filterExprToPolars` 的哲學一致。
- **難度**：L
- **可被 verify 守住**：可以。fixture SQL → 斷言節點圖；拒絕案例
  要斷言「有明確錯誤而不是產生一張空圖」。

### 4.5 分享連結 / 嵌入

- **目的**：讓別人看得到你的工作流。
- **適用情境**：貼給同事看；放進文件。
- **實作重點**：
  - **只分享工作流，不分享資料**。資料進 URL 會爆（且是隱私問題）。
    用 URL fragment + 壓縮（`lz-string` 之類），控制在數 KB 內。
  - 安全：共用連結裡的 SQL 會在**對方的瀏覽器**對**對方的資料**執行。
    沒有伺服器，所以沒有傳統的注入面；但一條刻意昂貴的查詢可以讓
    對方的瀏覽器卡死 —— 這是設計上的 DoS，要考慮執行時間上限。
  - 檔案來源的節點在對方那邊仍然是壞的（同 §7 的既有限制）。
- **難度**：M
- **可被 verify 守住**：可以。斷言「編碼 → 解碼」往返一致、
  「超過大小上限時明確失敗而不是產生斷掉的連結」。

## 建議的執行順序

已完成九項（1.1 / 1.2 / 1.3 / 1.4 / 1.6 / 2.5 / 3.1 / 3.4 / 4.5）。

剩下建議的順序：

1. **dbt 匯出（2.2）** —— 與 `ASSERT` 有綜效（ASSERT 可直接變成 dbt 的 tests），
   而且 `exportToSqlCte` 的依賴圖已經對了，缺的只是命名與檔案佈局。
2. **`IN_DB` 的誠實版（4.3）** —— 路線圖已定調：wasm 無網路，所以只能產生
   `COPY ... TO` 語句給有連線的環境跑。小，而且不必新增節點。
3. **OPFS（1.5）** —— 需要瀏覽器才能驗證，純決策邏輯可以抽出來測。
4. **Patch 預覽（3.2）** —— 管線已齊（`resolveAstPatch` + `auditAstPatch`），
   缺的只是 UI。

需要先處理前提的：

- **Macro（2.3）** 是架構改動：目錄的 `inputs` 目前是 `0|1|2|-1` 封閉集合，
  macro 有自己宣告的埠 → 目錄結構與 `resolveSourceTables` 都要改。
- **跨引擎等價（4.2）** 的前提未驗證：polars 有沒有 Pyodide wheel？
  **先寫 probe 再立項**，做不到就誠實地改成 Colab 交接。
- **SQL 匯入（4.4）** 需要 `sqlglot`（後端新依賴），要先確認能不能裝。
- **工作流快照測試（4.1）** 需要子行程，而目前的沙箱擋掉了 —— 等環境恢復。

**2.1 Alteryx 匯入不做**（產品定位），所以 Tier 2 剩下的是 2.2 / 2.3 / 2.4 / 2.5。

## 不建議做的

- **Pandas 匯出**：Polars 已經覆蓋，多一條路只會多一倍的跨引擎差異要守。
- **把資料上傳到後端**：會摧毀「資料不離開瀏覽器」這個目前最有價值的性質。
- **依賴 EXPLAIN 文字結構的功能**：版本一換就壞。
- **在瀏覽器裡連外部資料庫**：已實測為不可能（wasm 無網路）。
